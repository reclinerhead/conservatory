# The web app

`web/` is a Next.js 16 App Router app on the Aviary's stack: React 19 with the React Compiler, TypeScript, Tailwind CSS 4, `node:sqlite` for the database, pnpm, Vitest. It serves every page a person sees and writes the rows their actions create. It never calls Pl@ntNet or a language model.

## Running it

```bash
cd web
pnpm install
pnpm dev
```

`allowedDevOrigins` in `next.config.ts` lets a phone on the house subnet reach the dev server. `turbopack.root` there is the repo root, not `web/`: `app/globals.css` imports `design/tokens.css` from outside `web/`, and Turbopack reads nothing outside its root (without it `pnpm dev` panics on every page; the build only gets away with it because Tailwind inlines the import). The same root bounds the build's file tracing, which is why `lib/db.ts` marks its runtime database path `turbopackIgnore` both where it is built and where it is checked. `pnpm test` runs Vitest once; `pnpm build` is the production build the boxes run with `pnpm start`.

## Reading the database

`lib/db.ts` opens `CONSERVATORY_DB` with `node:sqlite`'s `DatabaseSync`: `openReadOnly` for pages (returns `null` when the file does not exist yet, so a fresh checkout renders honest zeros instead of crashing) and `openReadWrite` for the routes that record a person's actions (sets a 5 s busy timeout because Fern writes to the same file, and foreign keys on). The environment is read with bracket access (`process.env["CONSERVATORY_DB"]`) on purpose: Next inlines a static `process.env.FOO` at build time, and these values belong to the box at runtime. Pages and routes that read the database export `dynamic = "force-dynamic"` so their answers come from the request, never from the build. `dataDir()` resolves `CONSERVATORY_DATA` the same way.

## Adding a plant

Both of the README's flows go through the same page and the same route. `components/uploader.tsx` is the client side:

- **Two inputs.** "Take a photo" is a file input with `capture="environment"`; "Choose from the camera roll" is one with `multiple`. Either appends to the same list. Each photo gets an organ chip row (let it guess, leaf, flower, fruit, bark) that becomes Pl@ntNet's hint.
- **Shrink before sending** (`lib/shrink.ts`): `createImageBitmap` with orientation from EXIF, drawn to a canvas at most 1280 px on the long side, JPEG at 0.9. A 4 MB phone photo becomes about 300 KB, which is the difference between working and not on a weak Wi-Fi. If the browser cannot decode the file (HEIC on a desktop browser), the original is sent and Fern re-encodes it.
- **The date survives the shrink** (`lib/exif.ts`): the re-encode drops EXIF, so `DateTimeOriginal` is read from the original bytes first, by a minimal APP1 walk, and sent as `takenAt`.
- **One request per photo, with retry** (`lib/retry.ts`): four tries with doubling waits from 800 ms, so a drop on photo seven keeps one through six. A 4xx is `NoRetry`. Each row shows its own state and try count.
- **Then it polls.** Queued jobs are fetched from `/api/jobs/[id]` every 1.5 s until they settle, and the row shows the top species with its common name and score, "No match" for a rejection, or the error. That is the on-the-spot flow's answer; the confirm screen (#7) is where the name goes on.

`POST /api/photos` writes the file to `photos/yyyy/mm/<uuid>.<ext>` under the data directory (dated by upload in UTC, extension from the MIME type, anything unknown stored as jpg for Fern to re-encode), then inserts the `jobs` row and the `photos` row in one `BEGIN IMMEDIATE` transaction. Limits: 25 MB, image types only. `GET /media/...` serves originals and thumbnails with a year-long immutable cache behind `mediaRelPath`, a guard that accepts exactly the two shapes written into the data directory: `photos/yyyy/mm/<file>` from the upload route, and `reference/<species id>.jpg` or `.thumb.jpg` from Fern's enrichment pass. Photo names are UUIDs written once. A reference image can be rewritten in place by `python -m fern --enrich`, so `referenceUrls` adds the species' `enriched_at` as `?v=` and a re-fetched image is a new URL. A photo's thumbnail Fern has not written yet is answered with the original (`originalsForThumb` names the candidates), marked `no-store`, so a page shows the photo at once and the real thumbnail from the next load; anything else missing is a 404.

Tests: `lib/photos.test.ts` (paths, the media guard, the thumbnail fallback's candidates, MIME mapping), `lib/exif.test.ts` (the APP1 walk against hand-built JPEGs, both byte orders, the IFD0 fallback), `lib/retry.test.ts`.

## Naming a plant

`components/namer.tsx` is the confirm screen, one plant per screen, and it serves both flows: a person walking a strip of waiting photos, and one standing in front of the plant whose job has not settled yet (the screen polls `/api/jobs/[id]` every 1.5 s with the pill area reserved until Fern answers). What is on it, and why:

- **The pills** come from `lib/pills.ts` (`planPills`, pure, tested on the three shapes from the Phase 0 run). Three rules: the top three species lead when the best score is confident; when the top three agree on a genus and the best species score is under 0.30, a **genus pill** leads ("Echeveria · species unsure", scored from the API's genus row or, failing that, the sum of the species scores); when the best score is under 0.10 and the genera disagree, the screen is in its **low-confidence state** and the name field comes first. Scores stay on every pill, never shown as 0%.
- **One tap names it.** A pill, the "Name it" button, a roster chip, or "Same plant as the last one" all call `POST /api/jobs/[id]/confirm` and the save is immediate: there is no batch save. The route finds or creates the species (looked up by hand, case-insensitively, because `UNIQUE(scientific_name, cultivar)` does not catch two NULL cultivars), creates the specimen, links the job's photos and writes the `confirmations` row in one transaction. The optional **nursery-tag field** becomes the species' `cultivar`.
- **The name field** autocompletes over `GET /api/species`, the roster match: species the household already owns, most-owned first, so the second pot of anything is one tap. A typed name the collection does not know becomes a species row with the typed text as `scientific_name` and no GBIF id; the enrichment pass (Phase 2) resolves it.
- **Change** (`DELETE .../confirm`) reverses a naming cleanly: the confirmation goes, the photos unlink, the specimen is deleted if nothing else is attached to it and the species if no specimen is left, and the job is back in the strip. The pills were never discarded, so they reappear as they were. A job whose photos were all removed from the plant's page answers 409, since the strip would get a job with nothing to show.
- **Skip for now** is a link to the next waiting job; the skipped one stays in the strip. **Not a plant** is two taps on purpose (mis-taps are common) and then deletes the job, its photos and their files. **Add another photo of this plant** stores a second photo on the same job and sends it back to the queue; the old pills stay until the new ones arrive.
- **Next** goes to the next waiting job, computed server-side (`nextWaitingJob` in `lib/jobs.ts`, tested): the next later job, wrapping to the first, or the Conservatory when nothing else waits.
- **The first glossary marks** (#10) are here: confidence, scientific name, genus (with the plant's own genus as the example), species, cultivar.

## The collection

The life list on the home page is a grid of species, `components/species-grid.tsx` over the pure shape in `lib/species-grid.ts` (tested). A person opens the app to learn about a plant, and the species page is where the care sheet, the summary and the relatives live, so a tile opens the species and the species page's In your collection leads on to each plant. The server sends every species as a row (`speciesList` in `lib/species.ts`: names, genus and family, the living count, the living plants counted by place as a JSON array built in the same query, the count of plants gifted or died, when its newest plant was added, and the thumbnail); the client filters and sorts on the phone, so a search makes no request.

- **The tile** is the specimen card's recipe: the species' thumbnail 168 px tall (the photo that leads the species gallery, else the reference, else a tinted tile, the five greens varied between neighbours), then the common name in bold with the italic binomial under it, or the binomial alone in italics with that line reserved, so every tile is the same height. Then the meta line for the chip on screen (`tileLine`): at All, "3 plants · 2 places", the place's name when every living plant is in one place, or the count alone when none has a location; at a place or at "No location yet", "1 plant here" or "2 of 3 plants here"; at "No longer here", "1 plant no longer here". It says plants, not specimens, because a tile is one link and cannot carry the specimen info mark. The whole tile is one link to `/species/[id]`.
- **The filter row** (`placeChips`): "All" with every species that has a living plant, each place A to Z with the species that have a living plant there, then "No location yet" and "No longer here", each only when someone is in it. A species in two places counts under both; a species whose plants are all gifted or died is only under "No longer here". Counts come from the whole list, so the row never changes shape while a person types. Places match exactly as the plant pages write them, so "Shelf A" and "shelf A" are two chips, as they are on the tags page.
- **Sort by**, in the life list's header (`SortSelect`): Name, A to Z (the default, by the name the tile shows, then id) or Latest added (by when each species' newest plant was added, any status, newest first, then by name), applied by `gridRows` under every chip and search. The choice belongs to the device, not the view, so it lives in `localStorage` (`conservatory.sort`), not the URL, and survives a reload and a new session. The select and the grid read it through one small store with `useSyncExternalStore`, so they agree without a shared parent. The server draws Name, and a stored Latest added takes over on hydration. Every access is guarded, and a blocked storage keeps the choice in memory for the visit; a stored value not on the list reads as Name (`readSort`). The control is the Quarry's: a native `<select>` (the `.select` recipe), a drawn chevron, and every label invisible in the same grid cell so choosing never changes its width.
- **The search** lives in the top bar (`components/topbar.tsx`) and matches any part of the common name, the scientific name with cultivar, GBIF's spelling, the genus or the family (`matchesSpecies`), ignoring case. Typing a family name is the family filter. On the home page it filters as you type; anywhere else, Enter goes to `/?q=`. Search and chip combine.
- **Both live in the URL** (`?q=` and `?at=`), written with the native `history.replaceState`, which Next syncs with `useSearchParams`: the back button returns to the same view, the top bar's box and the grid agree, and nothing is fetched. An `?at=` that names no chip falls back to All. The top bar reads the URL behind a `Suspense` boundary because `/add` is static, and a static page can only read search params that way; the fallback is the same box, not yet live.
- **No match** draws the "nothing" card in the tile's shape with "Show every species", which clears both, beside two placeholder tiles drawn at a tile's exact height (`BlankTile`). "Showing 3 of 12 species" is always there, counted against the chip on screen. An empty collection draws "No species yet" with "Add the first one" in the same shape.
- **Pot tags** are printed from the Tags pill in the top bar, which opens `/tags` with every plant; the tags page has its own place chips, with the same keys as the grid's.

Specimen cards (`SpecimenCard` in `components/collection.tsx`, on the species page and nowhere else now) are DESIGN.md §4's: photo or tinted tile (one of the five tile greens, varied between neighbours) 168 px tall, then the names (`cardNames`): the common name (capitalised by `displayName`) with the italic species under it, "India Rubber Fig / *Ficus elastica 'Ruby'*", else the species alone. A plant has no name of its own: every plant of a species goes by the species' name, here, on its page, on its pot label and in the species gallery. One line under the name is always reserved, so when Fern finds a common name the text changes, not the height, and the meta lines line up across a row; the placeholder cards are drawn at the same height. Then "Location · since May 2019" (or "added Oct 2026" when no acquired date is known), and a tag for a plant no longer here. The whole card is one link to `/plants/[id]`. The species page's compact cards leave the common name out, since every card there is that species and its common name is the page's title; they reserve the same one line.

## A specimen

`app/plants/[id]/page.tsx` is one plant, read by `readSpecimen` in `lib/specimens.ts`: breadcrumb, the title block, tags for status, place and photo count, then the sections below. The title block is named the way its dashboard card is, by `cardNames`, and drawn the way the species page's is: the title is the common name, with the italic binomial (cultivar upright in quotes) under it; with no common name the binomial is the title and the line under it says "No common name on file". So a page reads "Tree Aeonium / *Aeonium arboreum*" or "*Ficus elastica* / No common name on file". The scientific-name info mark ends that line. The line is always drawn, so Fern finding a common name changes the text but not the height. The lightbox's dialog is named with the same name. The breadcrumb is Collection › the species › "Plant #142": the species crumb uses the same name, italic only when it is the binomial, and links to the species page, and the plant goes by its id, the number on its pot tag, since it shares the species' name. The tab title uses the species' name. The sections:

- **Photos as a timeline**, main photo first, then newest first by `taken_at` (upload time when the EXIF had no date). The main photo is the hero, two columns wide, served from the original (Fern's 1280 px re-encode); the rest are thumbnails. Every photo carries the mockup's dark caption pill, "Taken Oct 31, 2026" or "Added" when no date was in the photo, with " · Main photo" on the hero while there is more than one. A tap on any photo opens the lightbox on it (below), over the page.
- **The main photo** (#46) is the photo the plant is known by: the hero here, its collection card, its tile on the tags page, its photo in the species gallery and, when it leads that gallery, the species' thumbnail in the list and in Relatives. `specimens.hero_photo_id` (schema v6, [fern.md](fern.md)) holds the choice; NULL means the newest, so a plant nobody has chosen for looks as it always did. One order serves every one of those reads, `photoOrder` in `lib/specimens.ts`: the chosen photo, then `COALESCE(taken_at, uploaded_at) DESC, id DESC`. It is chosen in the lightbox: with more than one photo, each slide's footer offers "Use as main photo", or says "Main photo" in the same place on the one it is, so nothing shifts between slides. The button PATCHes `heroPhotoId` and refreshes; the lightbox holds its slide by key, not position, so when the refreshed page reorders the photos main first it stays on the photo just chosen, now 1 of N, and "Saving…" lasts until the page shows it as main. Focus goes back to the lightbox before the save, since the pressed button goes disabled and then gives way, and focus dropped on the page would leave Escape and the arrows dead. The tile's count line says how: "3 photos of this plant. Open one to choose the main photo." The PATCH answers 400 for a photo that is not the plant's own. The column goes with its photo (`ON DELETE SET NULL`, foreign keys on in both writers), so removing the main photo puts the plant back on its newest; Change on the confirm screen clears it in the same transaction when it unlinks the job's photos, so a plant never points at a photo not its own. Before v6 `hasHeroPhoto` finds no column: every read is newest first and the PATCH answers 503.
- **Remove a photo** (`components/photo-remover.tsx`): while a plant has more than one photo, each one carries a "Remove" pill in its top-right corner, in the caption's dark fill with a bin icon, a sibling of the photo's button so tapping the photo still opens the lightbox. The pill is smaller than its button, whose padding keeps the target at 44 px on the 120 px tiles. Two taps: the first turns it white and says "Yes, remove"; a tap anywhere else, Escape, or five seconds put it back. Every state draws over the photo, so nothing moves. `DELETE /api/plants/[id]/photos/[photoId]` answers 404 for a photo not on that plant, counts the plant's photos inside its `BEGIN IMMEDIATE` and answers 409 for the last one (so two tabs cannot take the last two between them), deletes the row, then unlinks the original and its thumbnail. Removing the main photo makes the newest the hero here, on the collection card and in the species gallery, which all read the same order. A photo that came through a job leaves the job, its candidates and its confirmation in place, because they are how the plant was named ("In your records", the species page's naming line) and the accuracy record; Change and Remove both allow for a job left with no photos.
- **Add a photo** (`components/photo-adder.tsx`) lives in the sage tile beside the timeline, and beside the species page's gallery (below). A person on a plant's page already knows which plant it is, so the photos go straight onto it: one file input (`multiple`, no `capture`, so a phone offers the camera or the library from one picker), the uploader's pipeline unchanged (EXIF date from the original, the shrink, one request per photo with four tries from 800 ms, a 4xx not retried), and none of its questions. `POST /api/plants/[id]/photos` takes `file` and `takenAt` with `POST /api/photos`'s limits, answers 404 for no such plant before storing anything, and inserts one `photos` row with the specimen set, no job and organ `auto`: no Pl@ntNet call, nothing in the strip, no new specimen. The tile's one text line is the count at rest and the status while it works ("Adding 2 of 3…", "Added 3 photos.", "Added 2 of 3; 1 failed: server 503."), reserved at two lines where the tile is a narrow column, so it never changes size; when the last photo lands `router.refresh()` redraws the timeline and the count from the server. Fern writes these photos' thumbnails on its idle sweep ([fern.md](fern.md)); until then the media route stands the original in.
- **The editable facts** (`components/plant-editor.tsx`): location (a `datalist` of every location in use, most plants first), acquired date, status as three chips. One Save button, enabled only when something changed, and a status line that says "Saved." in reserved space. `PATCH /api/plants/[id]` validates and returns the row.
- **Remove** is two taps, then `DELETE /api/plants/[id]`. The route deletes the photo rows (those added from the page included) and the jobs that brought them, found through the photos and through the plant's confirmations, since a removed photo's job has no photo left to find it by (an identified job with no confirmation would otherwise reappear in the waiting strip), the specimen, and the species if no specimen is left on it, then unlinks the files. The copy beside the button says that a plant that died or was gifted can keep its page by changing its status instead.
- **Its species** in the side column: species, common name (once Fern has found one), cultivar, genus and family, each with an info mark, then "Related to N other species you own" (`relativesLine`, linking to the species page's relatives block when N is above zero). The species page is the breadcrumb's middle crumb. "In your records" says how the plant was named (Fern's suggestion, typed, or as another photo of the last one) and when.
- **Pot tag**, last in the side column and only for a living plant: its code in the 84 px tile (`TagCodeBox`), "Tagged Oct 30, 2026" or "No tag yet", "Tag #142 opens this page", and "Print this tag" to `/tags?plant=<id>`.

## The species page

`app/species/[id]/page.tsx` is one species, read by `readSpecies` in `lib/species.ts` and shaped by the pure functions in `lib/species-page.ts` (tested). It is `design/mockups/species.html` in its Phase 2 subset. Everything on it is what Fern wrote: the confirm route's row, then the enrichment pass's columns (schema v2) and the care sheet (v3, see `fern.md`). The web app never calls GBIF, Wikipedia or the model.

- **Breadcrumb**: Collection › family › *genus* › this species (`speciesCrumbs`). A rank Fern has not filled is skipped, not faked. The genus is skipped for a species that is itself a genus. Family and genus link to `/?q=<name>`, the collection searched for them, which is the nearest thing to a family page.
- **Title block**: the common name as the title (GBIF's vernacular, first letter capitalised by `displayName`, since GBIF sends "echeveria" as readily as "India Rubber Fig"), else the binomial. Under it, the italic binomial with its author upright in `ink-3` and the cultivar upright in quotes, or "No common name on file" when the title is already the binomial. The scientific-name info mark follows the binomial, before the author, or ends "No common name on file". Both lines are always drawn, so filling the common name changes text, not height. Chips: the family (with its info mark), "Known to genus" for a genus-rank row, and "N in your collection" (living). On the right, the mockup's "Print pot tags" (soft) goes to `/tags?species=<id>`; "Add a specimen" is not drawn, since adding goes through Add a plant.
- **Gallery** (`speciesGallery`): each specimen of this species shown by its main photo (the chosen one, else its newest), newest first by that photo's date, then the reference image. The owner's photos always outrank the reference, so the reference is the hero only when the household has no photo of this species. The hero spans two columns (320, 420, then 560 px tall by width), the second item fills the right column, the third is a 120 px tile beside "N of your photos · 1 reference image" and "Add a photo" (below); more go in a row of tiles below. Every photo opens the lightbox on it. Under each slide, its caption and the link the photo used to be: "Open Ficus elastica" to its specimen's page for an owner photo, and for the reference "The image and its licence on Wikimedia Commons" (a new tab), so the licence stays one tap from the image. The reference carries the stored credit ("Ficus elastica · Wikipedia") in its caption. An empty second slot is a dashed placeholder that says why: no reference fetched yet, none on Wikipedia, or "your own photo takes the lead here".
- **Add a photo** beside the gallery is the plant page's adder (`components/photo-adder.tsx`, `compact`: the 40 px button, both lines always reserved), so a photo of a plant you already have goes straight onto it and never through `/add`, which would make it a new job and, one tap later, a duplicate specimen. The plants it can take are `photoTargets` (tested): the species' living plants, else, when none is living, the rest, newest first, each named by its pot tag number and place, "Plant #142 · Kitchen". With one, the button opens the picker. With several, the select from DESIGN.md §4 comes first, its placeholder "Which plant?" standing in for the label a column this narrow has no room for, and the button stays disabled until a plant is chosen. The done line names the plant ("Added 2 photos to Plant #142 · Kitchen."), since the gallery shows each plant by its main photo and a new photo may not appear in it. The refresh redraws the gallery and "N of your photos". The adder sits beside the 120 px tile while the column leaves it 9.5 rem, and wraps under the tile where it does not (640 to about 1000 px), so neither the select nor the button is squeezed. A species with no plant at all, which the remove route never leaves behind, gets "Add a plant" to `/add` in its place.
- **About this species** (`aboutState`): the Wikipedia lead as paragraphs, with the species' own Latin names set in italics (`latinRuns`, since the plain-text extract has lost its markup), then "Summary from Wikipedia · fetched <date>" and the article link. Before Fern has looked the species up, a reserved sage block says so; after a look that found no article, it says Wikipedia has no page and, when GBIF had no match either, that the name may be a trade name or a slip. There is no Refresh button: re-enrichment is `python -m fern --enrich <id>` on the box.
- **Care sheet** (`careState` in `lib/care.ts`, tested; `CareBlock` in the page; `components/care.tsx`), between About and In your collection: the mockup's six cells (light, water, soil, hardiness, fertilizing, dormancy), three across, two from 640 px, one on a phone, each labelled with its info mark. A written cell is the headline, two or three sentences, and "N figures and what they rest on", a button that floats a sage note listing each figure with its value and basis, so opening it moves nothing. The header says what the sheet is for (`careScopeLine`: "For zone 6a · written once for this species", or "written for the genus Echeveria"); the hardiness mark's example puts the household's zone beside the sheet's headline. The foot says who wrote it (`careWrittenLine`: "Written by Claude Sonnet 5.5 on <date> from GBIF's taxonomy and Wikipedia's summary", with the gateway slug turned into a name by `modelLabel`), prefixed for a genus-level sheet with why it is written for the genus. Beside it, Rewrite, which posts to the rewrite route and refreshes. All six cells are always drawn at the height of a written one, so before a sheet exists each holds sage skeleton bars and the foot says why, in this order: a stored sheet always shows, even with no model configured now; else no model configured ("It needs AI_GATEWAY_API_KEY"); else GBIF has not placed the species, or could not; else the last attempt failed, with its date and error and "tries again a day later"; else Fern is about to write it. In that last state the page refreshes itself every 5 seconds for up to 3 minutes ("Fern is writing it now"), so a Rewrite comes back without a reload. When a rewrite after a prompt or zone change fails, the earlier sheet stays and the foot says so. The web app knows a model is configured only by `AI_GATEWAY_API_KEY` being set in its own environment (both units read the same file); it never reads the key's value. `readCareRow` checks that the table exists, so the page renders against a database Fern has not migrated yet.
- **In your collection**: every specimen of the species as the collection's specimen card in its compact variant (`SpecimenCard compact`: 140 px, 16 px radius, the mockup's `rel`), grouped by location exactly as the collection groups them, with "3 specimens · 2 locations · 1 no longer here" in the header (`inCollectionLine`).
- **Relatives you already have** (`relativesOf` in `lib/relatives.ts`, tested), `#relatives`: the household's other species with the same genus, then those with the same family under a different genus, each group most owned first, then by name. It is a filter over the home grid's rows (`speciesList`), so a relative card carries the same thumbnail rule: the photo that leads the species gallery, else the reference, else a tinted tile. Cards are the mockup's `rel`: 120 px image, the name, the binomial under a common name, "N specimens", one link to that species' page, four across (three, then two on a phone). Taxonomy only: same genus, same family. Lineage is a different relationship and never feeds this, and nothing is suggested from GBIF. A species with no living specimen is not a relative. Genus and family match ignoring case and stray spaces, since the confirm route writes Pl@ntNet's spelling before Fern writes GBIF's. The block is always drawn. An empty group is a dashed cell ("No other *Ficus* yet"). A placed species with no relatives gets one reserved panel, "Nothing else in this genus or family yet". A species missing either genus or family is not placed, and the panel says Fern has not placed it yet or, after a pass, that GBIF could not. The genus and family marks take their examples from the plants on screen (`genusExample`, `familyExample`: "Ficus elastica and Ficus lyrata are both Ficus"). A footer, "Every species in Moraceae", links to `/?q=<family>`.
- **Taxonomy** in the side column: kingdom, phylum, class, order, family, genus and species, every row always drawn with its info mark, and the owner's cultivar. ## The lightbox

A photo on the plant's page or the species page opens full size over the page, which stays where it was (#46). `components/lightbox.tsx`: `PhotoLightbox` wraps the page's photo section with its slide list and holds the open slide by key; `OpenPhoto` is a photo as a button (`cursor-zoom-in`, labelled "See the photo taken Oct 31, 2026 full size") that opens it there; both pages stay server components. The library is `yet-another-react-lightbox`, pinned, with its Zoom (pinch, scroll wheel, double tap, up to three times the photo's own pixels) and Counter ("2 of 5", with more than one slide) plugins and nothing else: the page's grid is the thumbnails, and the viewport is the size. Slides are the stored originals in the page's order; arrows, swipe and the keyboard move through them without wrapping; Escape, Close and a tap on the backdrop close it. Each slide's footer (`render.slideFooter`) is the page's caption pill at the left and one action at the right (the main photo control, or the species page's link), wrapping to two rows on a phone; it lets taps through between the two, so the backdrop still closes. Its look comes from the tokens in `globals.css` (the ink backdrop at 96%, surface-white buttons without the library's drop shadow, a visible focus ring the library would otherwise remove, the counter at `text-meta` bold); the stylesheets are imported by the component, so only the two pages that use it load them. Rejected: PhotoSwipe (no React; a hand-written wrapper) and a Thumbnails strip (the page already is one).

## Pot tags

Every plant gets a QR label for its pot that opens its page from the phone's camera (#36). The pure parts are `lib/tags.ts` (tested), the code is drawn by `lib/tag-code.ts` on the server, the print page is `app/tags/page.tsx` over `components/tag-printer.tsx`, and the sheet is the `label-sheet` recipe in `globals.css`.

- **The address.** A tag encodes `<CONSERVATORY_URL>/t/<specimen id>` (`tagUrl`). `/t/[id]` sends a plant still in the collection, living or gone, to `/plants/[id]` with `redirect()`, an HTTP 307: temporary, because a phone caches a 308 and what a scan opens is meant to change later (a last-watered page, #3's cutting flow) without reprinting a label. The segment has no `loading.tsx`, so the redirect is never streamed as a meta tag. A removed plant's tag gets a small "no longer in the collection" page, and since specimen ids are never reused (schema v5, [fern.md](fern.md)) a tag cannot open the wrong plant. The short path keeps the code at version 3 (29 × 29 modules) at error-correction level Q. Rejected: encoding `/plants/[id]` (what a scan opens could never change), and a separate tags table with codes of its own (no sheet could be drawn without first writing rows, and the label's number would not be the plant's).
- **`CONSERVATORY_URL`** is read at runtime with bracket access (`tagBase`) and never taken from the request, since a sheet printed from the dev server would otherwise put a dev address on labels that last years. Unset, or not http(s), no code is drawn anywhere: the label's code square and the cards' 84 px tile are dashed placeholders that say why, Print is off with a line saying what to set, and nothing moves. On orchid it is `https://conservatory.lan` ([ops.md](ops.md)); at the desk, the dev server's LAN address, so a phone can scan a test print. `/tags` shows the host the codes point at.
- **Drawing a code.** `qrcode`'s `create()` at level Q, on the server only; `codePath` turns the module matrix into one SVG path, a rectangle per horizontal run, drawn in JSX by `TagCodeSvg` (`components/tag-code.tsx`) in pure black rather than `ink`, because a mono laser prints a near-black as a dot screen and blurs the module edges. No `dangerouslySetInnerHTML` and no QR library in the client bundle: `/tags` sends each row's path with it. The client imports `lib/tags.ts`, so that file must never import `qrcode`.
- **The stock** is the 1″ × 2⅝″, 30-up address label in the Avery 5160 layout (½″ top margin, 3⁄16″ sides, 3 across at a 2¾″ pitch, 10 down at 1″), which its weatherproof versions share. `label-sheet` writes it once in `em`, with 1em one inch of paper: on screen the sheet's font-size is its frame's width over 8.5 (`.label-sheets` is a size container, `100cqw / 8.5`), so the preview is the printed sheet's own markup scaled to fit; in print it is `1in`. A label is the code at 0.78″ with 0.11″ of the label's white round it as its quiet zone, then three one-line, ellipsised lines from the card's naming rule (`cardNames`): the name, the italic species, and "Shelf 2 · #142" (or "#142"), so a label means something without a phone. The paper's sizes and its black on white are the one place `globals.css` picks values outside the tokens.
- **Printing.** `@page { size: letter; margin: 0 }`, and in print only the sheets: anything that neither holds `.label-sheets` nor sits inside it is `display: none` (by `:has()`), and what holds it loses its margins, padding and borders, so sheet one starts at the top left corner of page one. Each sheet breaks after itself but the last. Label outlines, used labels and the sheet captions are screen only. The page says to print at 100%, not "fit to page", with margins none, and to try plain paper against a sheet first. Rejected: a PDF made on the server (exact without print settings, but a dependency and a download step; revisit if a printer disagrees).
- **Choosing.** `/tags` lists every living plant, one row each (a 44 px checkbox, the 56 px thumbnail, the name and species, "Shelf 2 · #142", and "Tagged <date>" or "No tag yet"), grouped by place as the collection is. The collection's location chips (same grouping, same `?at=` values) and a "Not tagged yet" toggle (`?untagged=1`) narrow it, and `?species=` or `?plant=` narrows it to one species or one plant, with "Show every plant" to clear. All of it runs on the client over the rows the server sent, kept in the URL with `history.replaceState`. On arrival the untagged plants on screen are checked; a plant asked for with `?plant=` ("Print this tag") is checked whatever its state. What prints is what is checked and on screen, in the list's order.
- **Start at label N** (`sheetSlots`, `nextStart`), for a partly used sheet: a 3 × 10 map of 44 px cells; tapping the first free label marks the ones before it as used (struck through) and shades the ones this print fills. Labels beyond the first sheet flow onto further sheets, each from its label 1. After Mark as tagged the page keeps where the print stopped in `localStorage` (`conservatory.tags.nextStart`, per browser, every access in try/catch) and offers it as the next start; it is read through `useSyncExternalStore`, so the server render starts at label 1 and nothing else moves when the browser's value arrives.
- **Mark as tagged.** The page cannot tell a printed sheet from a cancelled dialog (`afterprint` fires for both, Ctrl+P included), so when the dialog closes a strip asks "Did they print? Mark these 12 as tagged." Its space is always kept. `POST /api/tags` with `{ ids }` (1 to 600 positive integers) stamps `tagged_at` on those still living in one `UPDATE ... json_each` and returns the count; the page then refreshes, and the specimen card, the species card's count and "Not tagged yet" all read the same column. Rejected: marking when the sheet renders or on `afterprint`.
- **Before v5** the column does not exist: `hasTaggedAt` checks for it, so every page renders against a database Fern has not migrated yet with every plant untagged, and the mark route answers 503.

Not built: a scan page that says when the plant was last watered (needs the event log), the cutting-of-this-plant flow (#3), other label stocks, a printer offset nudge, and a scanner inside the app (the phone camera already does it).

Tests: `lib/tags.test.ts` covers `tagUrl` (trailing slashes; unset and non-http(s) bases), `codePath` (a hand-made matrix, every dark module covered and no light one), `sheetSlots` (no sheet for no tags, the used labels before the start, flowing onto further sheets, the last sheet's count, the clamp to 1..30) and `nextStart` (wrapping after label 30). The routes, the redirect and the components are checked by hand.

## The glossary

`lib/glossary.ts` holds every term the app explains (scientific name, genus, species, family, cultivar, specimen, confidence, common name, organ, and from the species page taxonomy, kingdom, phylum, class, order, author, and the care sheet's light, watering, soil, hardiness zone, fertilizing and dormancy), keyed by slug, two or three plain sentences each with a "more" link. `components/term.tsx` is the info mark from DESIGN.md §4: an 18 px ring after the term, an "i" in moss, and on tap a sage note that explains it. The note floats under the mark rather than expanding in place, so opening one never moves anything: the no-layout-shift rule outranks the mockup's inline block. An optional `example` lets a screen add a sentence about the person's own plants. `lib/glossary.test.ts` scans every `.tsx` for `<Term k="...">` and fails on a key the glossary lacks, and keeps every entry to a short paragraph. A key passed as a value rather than a literal (the care cells' `CARE_CELLS[].term`) is typed `GlossaryKey`, so the compiler checks it instead.

## The visual language

Defined in [`design/DESIGN.md`](../../design/DESIGN.md), made with Claude Design before any screen was built: pale sage ground, white cards, one moss action colour with pink, amber and blue reserved for bloom, time-sensitive and water, pills for everything pressable, Fraunces for display and Nunito Sans for reading. Read it before touching UI; the two static mockups in `design/mockups/` are the reference for the dashboard and species pages. How the app wires it:

- **Tokens.** `design/tokens.css` is the Tailwind 4 `@theme`, imported from `app/globals.css`. Nothing else in `web/` defines a colour, a face, a radius or a size: a screen says `bg-sage`, `text-ink-2`, `rounded-card`, `text-h2`, `max-w-page`.
- **Fonts** are self-hosted through `next/font` in `app/layout.tsx` (Fraunces with its italic for binomials, Nunito Sans at 400, 600, 700); the variables they set feed the two font tokens, so the boxes make no font requests. The Google Fonts `@import` that DESIGN.md's tokens originally carried was removed for this reason.
- **Component recipes** (DESIGN.md §4) are written once in `globals.css` under `@layer components`: `btn` with `btn-primary`, `btn-soft`, `btn-ghost`, `btn-compact`; `chip` with `chip-on`, `chip-compact`; `card` with `card-link` for the hover lift; `tag` with `tag-bloom`, `tag-warn`, `tag-water`; `nav-pill`; `thumb`; `sp` for an italic Latin name; `field` for a text input in the chip's pill.
- **The top bar** (`components/topbar.tsx`) is in the root layout: leaf mark and wordmark, the five nav pills (Collection, lit on `/`, on a species page and on a plant's page, and Tags, lit on `/tags`, are links; Locations, Reminders and Flower Show are drawn in place, muted, so the bar keeps its shape), the search box, the primary "Add a plant". The search is live on `/`; anywhere else, Enter goes to `/?q=`. On a phone it is three rows (wordmark and Add, nav, search); from 640 px the nav joins the first row and from 1024 px the search does too, giving up width (260 px down to 180) before anything wraps, so the bar is one row at 1280 px.
- **The dashboard** (`app/page.tsx`) follows DESIGN.md §5 in its Phase 1 subset: the pending strip (a sage card with three overlapping thumbs, real ones when photos are waiting, the headline and one primary button), the life list with its counts line, location chips and grouped 3-across specimen cards (1 below 640 px, 2 below 1024), and the side column's "at a glance" stat tiles. The counts line and the tiles count living plants; the "All" chip counts every card, the gone ones included. Greeting, Today's care, the other filters, Blooming now and the Flower Show wait for the phases that have data for them; their space is not faked.

### Rules every screen keeps

- **No layout shift.** Empty states reserve the populated space. The pending strip keeps its height in every state and lays out its button even when hidden; the life list's empty state is drawn in the specimen card's own shape. Counts render on the server.
- **Honest zeros.** The counts say "0 specimens" rather than hiding.
- **Phone first, laptop wide.** Rows wrap, the side column is a flex sibling that drops below on a phone, card grids step down by width, chip rows wrap and never scroll sideways.
- **Tap targets** are at least 44 px tall, the buttons and chips 44 by recipe.
- **The app teaches** (#10). Every horticultural term carries an info mark; the glossary component lands with the confirm screen.
